# Payment operations additions — review and walkthrough

Owner approved deployment and Git push on 12 October 2026. Backend and website are now deployed with public checkout disabled; current versions and live evidence are in `payment-deployment-20261012.md`. The evidence/deployment-plan sections below describe the earlier local review, superseded by that report. No order, charge, capture or refund was made by the agent. Public activation settings were not changed.

## What changes

1. **Recent paid orders:** admin Payments shows paid/refunded entries newest first, stored contact/project details and an acknowledgement toggle. A separate sidecar stores the first paid confirmation time and acknowledgement. Existing records are backfilled from their stored verification time (this is not a verified provider capture timestamp). The Overview banner and existing Payments badge count unacknowledged entries. Toggling acknowledgement never writes settlement fields.
2. **Needs investigation:** unknown signed webhook payment references are atomically recorded with the existing unique event-ID marker, returning 200 for duplicates. The scheduled GET-only order scan matches provider `receipt` to unattached server reservations older than 15 minutes, then rechecks that the reservation is still unattached inside SQL. It records evidence only; it cannot attach, settle, fulfil or create orders. The list/banner intentionally retain investigation evidence; no manual paid or resolution override was added. Historical unknown events without payment metadata cannot be reconstructed automatically.
3. **Lost disputes:** distinct alerts persist until an admin acknowledges the dispute. Acknowledgement is by dispute identity, so a webhook replay or scheduled snapshot cannot reopen the same acknowledged loss. Open-dispute warnings continue to clear on won/closed. A later closed event cannot erase an unacknowledged recorded loss. No dispute event changes the paid ledger.
4. **Scheduled recovery:** after the existing pending check, the same scheduled function re-fetches paid/refunded orders confirmed within the last 30 days, using the existing provider validation and monotonic reconciliation writer. Paid cannot become pending/failed; refunds retain the existing partial/full refund semantics. The new dispute sync uses `GET /v1/disputes?count=100&skip=...` and GETs linked payments, storing minimal current snapshots and deduplicated audit entries. No evidence or customer data is copied from disputes. Permission/API errors fail the run visibly instead of being treated as an empty dispute list. Provider reads and history are paginated and retain the existing 110-second run budget; a run that cannot finish is flagged. Large-volume runtime/load behaviour remains unverified.
5. **Receipt:** success screens request a separate link after verification. The URL uses a random UUID signed with a dedicated HMAC secret and contains its token in the fragment (`/receipt#...`), avoiding URL/request/referrer logs. The anonymous reader verifies that signature and projects only package, amount and current saved status. It never calls Razorpay or settlement. It works while public checkout is disabled and without browser session storage. Receipt routes suppress tracking/replay/promotions, are noindex/no-store/no-referrer and have no checkout controls. A bearer link should be kept private.

The existing paymentAction, callback verification, checkout authorization, recordStatus and fetchStoredPaymentStatus bodies are unchanged. Existing settlement migrations/functions are unchanged. The added observer writes only sidecar metadata in the same database transaction. If sidecar storage fails, the transaction fails closed; it cannot report a paid receipt without a saved settlement.

## Deployment order after owner approval

1. Keep both public activation flags false. Review the diff and apply the four new migrations in timestamp order: payment_operations, payment_investigations, payment_dispute_acknowledgements, payment_dispute_sync.
2. The owner reports saving a random 64-character `PAYMENT_RECEIPT_SECRET` in **Supabase Edge Function secrets** on 2026-10-12. Its live configuration has not been independently checked; no value was read or printed. It is required for receipt links only. Do not place it in a VITE variable or the website. For local Edge tests use the ignored Edge environment file. Keep it stable; when rotating it retain the old value as `PAYMENT_RECEIPT_PREVIOUS_SECRET` while old receipts need to remain valid. One previous key is supported; removing it invalidates links signed with it.
3. Deploy backend **before website**: updated razorpay-webhook, razorpay-payments and razorpay-reconcile with their shared modules. Preserve the existing custom authentication configuration and scheduler credential. Do not change keys, webhook signature configuration, public activation or checkout settings.
4. Check schema/grants, rejected bad signatures/non-admin calls, signed receipt projection and a scheduled completion with GET-only recovery. Account access to dispute listing and actual relational query shapes must be verified here. No charges are required for these read-only checks.
5. Only then deploy the website while preserving runtime bindings and public payments disabled. This document is a review/deployment plan, not authorization to execute it.

## Admin walkthrough after deployment

1. Log in at `/admin`, open Overview: previously paid entries backfilled by migration should show an unacknowledged-paid banner and Payments badge.
2. Open Manage → Payments → Recent paid orders. Compare the previously recorded test payments/contact details against Razorpay (six paid ledger rows at deployment). Toggle Acknowledged; return to Overview and refresh. That entry must stop contributing to the paid banner. Uncheck it to verify reappearance.
3. Open Needs investigation. It displays references only, with no Attach/Mark paid action. Empty production data is not proof of unknown-payment ingestion; use isolated fixtures/Test Mode for that case.
4. A lost dispute fixture should appear distinctly in the banner and queue; click Acknowledge lost dispute and refresh. A repeated webhook or scheduled snapshot of that dispute must not re-alert. Do not manufacture a live dispute to test this.
5. Check last successful reconciliation time after the next scheduled run. For a missed-refund test, use a controlled Test Mode fixture with webhook suppressed and a dashboard-issued refund, then wait for recovery. A live refund moves real money and needs separate owner authorization.
6. Use Check status for an existing confirmed admin test to request its Payment receipt link (no new payment). Copy that full link to another device/private window and refresh it. Confirm only package, amount and status appear. A modified signature must fail. Receipt pages must offer no payment action, even while checkout is disabled.
