A prospective client opens an architect's project gallery on a phone while travelling between meetings. The photographs are impressive, but the page jumps as each image arrives. There is no explanation of whether the practice designed the building, its interiors or only the façade. The visitor leaves with an aesthetic impression and no reliable basis for commissioning work. That is an information-design problem before it is a marketing problem.

For a Mumbai architecture practice, the website should make the work legible: what the brief was, what constraints shaped it, what the practice delivered and how an appropriate enquiry begins. This guide describes a proposed implementation approach, not a claim about measured results for an architecture client.

Make each project a readable design argument

Start with a small number of documented projects rather than an enormous image wall. Give each project a stable URL, a descriptive title and a concise account of the commission. Building type, broad location, stage and the practice's actual role help a reader interpret the images. Distinguish a completed building from an unbuilt proposal and a competition entry. A rendering should be labelled as a rendering, especially when it sits beside construction photographs.

Write about constraints the team can substantiate. A compact site, an occupied renovation, a phased construction schedule or a particular daylight requirement gives the reader something to evaluate. Describe the design response in ordinary language. Avoid inventing energy savings, budget figures or client approval quotations merely to make the case study look complete. If an outcome was not measured, show the design decision and its limitation instead.

Project credits matter too. Identify collaborators and photography permissions, and agree what may be published before preparing the gallery. Residential clients may not want an exact address, detailed floor plan or recognisable personal possessions online. A broad neighbourhood and selected drawings can communicate architectural thinking without exposing the household. Public portfolio access and confidential project delivery should use separate systems.

Build a gallery that stays still while images arrive

Architecture imagery often has mixed aspect ratios. Generate several image widths and use responsive image markup so a narrow phone does not receive the same file as a large desktop. Offer AVIF or WebP where your image pipeline supports them, retain a compatible fallback, and inspect fine drawings for compression damage. A smaller file is useful only if captions and important design details remain readable.

Set width and height attributes or a deliberate aspect ratio for every gallery tile. The browser can then reserve space before the image downloads, reducing layout movement. A masonry effect should not continually rearrange already visible work as dimensions become known. A simple grid with predictable rows is often easier to browse, navigate with a keyboard and maintain than an elaborate layout whose visual order differs from its reading order.

Lazy-load images below the opening viewport. The main project image, if it is the Largest Contentful Paint candidate, should be discoverable in the initial HTML and should not be lazily loaded. Measure the actual candidate before assigning high fetch priority. Giving every image high priority merely makes them compete. Google's LCP guidance explains why discovery time and resource priority need to be considered together.

Separate the public portfolio from drawing delivery

A Cloudflare CDN can cache public, versioned images close to visitors, but it does not make a confidential drawing safe to publish. Give public image files content-based or versioned names so a revised image can receive a new URL. Avoid putting client documents behind a guessable path and treating the absence of navigation as access control. A public bucket remains public even if no menu links to it.

For private files, use authenticated access or short-lived authorised links and appropriate cache headers. Check the actual response through the delivery path rather than assuming that an application setting controls every intermediary. Cloudflare documents how origin cache directives affect shared caching. A practice should decide who can access drawings, how long access lasts and what happens when a project ends.

Ask questions that establish whether the commission fits

An architecture enquiry should establish project type, broad site location, approximate scale, stage and the service being requested. A person seeking an interiors refresh should not accidentally submit a new-build brief. Keep approximate budget and schedule questions clear about their purpose, and permit uncertainty where the visitor is still investigating feasibility. Do not request title documents or identity records through the first marketing form.

Send an explicit acknowledgement after the server has accepted the request. Explain that the team will assess fit and availability; submission is not acceptance of the commission. Record a minimal enquiry reference so a visitor can discuss the request without resending the entire brief. Notify the practice through a reliable channel, and test what happens if notification delivery is delayed after the enquiry itself has been stored.

Commission the content system, not just its opening screen

Before approving the build, ask a staff member to add a project using real photographs, a long title and incomplete metadata. Check that they can reorder images, add credits, remove a withdrawn photograph and change the project stage without developer intervention. Confirm how redirects are maintained when titles or slugs change. A portfolio becomes stale quickly if updating it requires editing source code that the practice does not own or understand.

Review the final site on a narrow phone with a cold cache and a slower connection. Navigate project pages without relying on hover, open the enquiry form using a keyboard, and confirm that image alternatives describe meaningful content rather than repeat search phrases. The result should let a potential client understand the practice's decisions and make a well-informed approach. That is a stronger brief than simply asking whether architects need another online presence.
