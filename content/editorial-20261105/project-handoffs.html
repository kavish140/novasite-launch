A website project is easier to review when each stage produces something concrete: an agreed scope, a page map, a working interaction and a handover record. A calendar alone does not show whether those decisions have been made. Use the checkpoints below to discuss a project with its developer without assuming every business needs the same pages or integrations.

Start with one customer task and its boundary

Describe the action a visitor should complete. For a clinic it might be requesting a consultation; for a wholesale supplier it might be sending a list of products and quantities for quotation. Write down where the website's responsibility ends and where staff take over. A consultation request is not necessarily a confirmed appointment, and a quote request is not a paid order.

These distinctions appear in SiteNova's existing project descriptions. The Dr. Dipti Ganatra clinic project organises practitioner-approved treatment information and a consultation enquiry journey. The Corporatezone project documents a nine-category wholesale catalogue and a consolidated enquiry basket. Their different tasks justify different structures; neither description establishes a measured increase in leads.

Agree what the owner must supply

Before detailed design, identify approved text, images, product information, contact details and any credentials or permissions needed for integrations. Name a person who can approve each item. If a logo or photograph is provisional, label it in the review rather than allowing it to become final by accident.

For a professional practice, the practitioner should approve service descriptions and credentials. For a catalogue, the supplier should approve product codes, units and specifications. The developer can organise and implement that information, but should not invent certifications, customer reviews, stock quantities or performance results to fill a layout.

Review the page map before polishing screens

List the necessary pages and the route between them. Check whether a visitor can reach the selected task from the homepage, a shared product link and a search landing page. Record pages that require private access and keep them out of public navigation. Explain which existing URLs need to remain stable if this is a replacement website.

Review one representative page in enough detail to settle hierarchy, navigation and content responsibilities. Use a real long service name or a product with multiple variants rather than only short placeholders. This exposes layout and information problems while they are still inexpensive to discuss.

Ask to see the unsuccessful interaction

A working demonstration should include an empty result, invalid input and an unavailable service. For an enquiry, ask what happens if the visitor presses Submit twice or the network fails after the server accepts the request. The response should not claim successful storage merely because an animation completed or an email application opened.

Agree the acceptance criteria before signing off the interaction. A useful criterion might be: the accepted enquiry receives a reference, a repeat click does not duplicate it, and a failed request retains enough information to retry. Those are proposed checks, not a claim that every past project contains the same storage or recovery mechanism.

Prepare launch as a controlled change

Record who controls the domain, DNS, hosting, content accounts and notifications. Confirm the destination and recovery plan before changing DNS. Check public pages, redirects, contact routes and essential integrations in the production environment after release. A local preview cannot establish that a live email recipient or third-party account is configured correctly.

Test on relevant phones and browsers, check keyboard access and inspect load and interaction behaviour. Retain the URL, date and conditions for any published benchmark. A good score does not confirm that a form works, and a functional form does not establish that every page is fast.

Hand over decisions as well as passwords

The handover record should explain how approved content is updated, who receives enquiries, which services renew and how access is recovered. Share sensitive access through the agreed private process. Keep private customer records and tokens out of public documentation and analytics.

Assign responsibility for ongoing checks: content accuracy, integration health, renewal dates and recovery readiness. Define the actual support arrangement instead of implying unlimited maintenance. The practical result is a website the business can operate, with known responsibilities and explicit limitations. SiteNova's agreed proposal determines the work included in a particular engagement.
