A delayed mobile menu and a fall in search traffic are two observations that need separate investigation. Interaction to Next Paint (INP) helps diagnose responsiveness, but it does not establish why a page lost rankings. INP replaced First Input Delay as a Core Web Vital on 12 March 2024; it is not a new 2026 penalty.

This guide describes a repeatable investigation for a business website. The examples are diagnostic scenarios, not measured client results. Start with a control people actually use, retain the evidence, and check that improving responsiveness also preserves the underlying task.

Separate a slow interaction from a search incident

If enquiries fell, first establish what changed: impressions, search clicks, visits, accepted requests or completed business. Check the affected pages, dates and devices in the available reports. A broken form, changed tracking configuration, removed page or different demand can require a different response from a slow interface. Do not buy a rebuild based only on a disappointing score.

Google explains that INP became a Core Web Vital in March 2024. That history matters when evaluating an article claiming a newly introduced threshold. A performance change on your own site still needs its own evidence; the calendar year does not explain it.

Write down the interaction before opening a test

Choose a specific task such as opening a product filter, expanding consultation details or adding an item to an enquiry basket. Record the route, viewport, device, browser and whether the visit is cold or benefits from cached assets. Include the sequence that leads to the slow action. An idle homepage recording cannot reveal work triggered only after a visitor opens a large catalogue.

In an illustrative product filter, the useful visible outcome is an updated result count and list. Record whether the tap is acknowledged, how long results take to appear, whether keyboard focus remains useful and whether selecting a second filter loses the first selection. Those observations help distinguish slow rendering from a failed action or confusing feedback.

Read field data without inventing a missing measurement

Use the field-data section of PageSpeed Insights when it is available, and note whether it describes the specific URL or the whole origin. An origin-level observation may combine pages with different layouts. If there is insufficient eligible traffic, label field INP unavailable. A missing number is not a zero and does not prove that visitors experience no delay.

Google's INP optimisation guidance describes a good result as 200 milliseconds or less, assessed at the 75th percentile of page loads and segmented by mobile and desktop. A controlled browser recording is useful for finding causes, but it is not a replacement for that real-user observation window. Keep the two kinds of evidence labelled.

Follow the work between the input and the next paint

Record the chosen interaction in browser performance tools. Look for work already occupying the main thread when the input arrives, the event handler's own work and the rendering needed to display its result. The same visible delay can have different causes. Loading another library or changing the hosting provider without locating the work can leave the problem intact.

For the catalogue example, inspect whether every keystroke filters and rebuilds the entire list. Try a smaller representative dataset, then restore the full one. If work grows with catalogue size, investigate the filtering and rendering path. If an unrelated third-party script occupies the thread first, investigate that script separately. Change one plausible cause and retain the before-and-after recordings.

Make the smallest change that survives task testing

  • Break up expensive work where the application can safely yield, and avoid repeating calculations for unchanged inputs.
  • Reduce unnecessary updates and layout work before replacing an entire framework.
  • Load optional features when needed, after considering consent, accessibility and the feature's purpose.
  • Provide immediate, accurate feedback while a request is pending. A painted spinner does not establish that the server accepted an enquiry.

Do not attach every deferred script to the first tap indiscriminately: doing substantial extra work on that interaction can make it worse. Equally, do not remove a required form-validation or accessibility feature just to improve a synthetic result. A useful optimisation preserves the business task and handles failure clearly.

Retest slow and unsuccessful journeys

Repeat the original action under comparable conditions, then exercise keyboard input, slower devices and error responses. For a submission, check repeated clicks, a network timeout and recovery after refresh. Confirm that the server receives the intended request once, that entered data remains recoverable where appropriate and that the interface does not claim success prematurely.

Keep an investigation record with the route, date, environment, trace, hypothesis, exact change and retest result. State which behaviours were mocked or unavailable. For a broader measurement procedure, use the trace-to-retest performance guide; its retained URL is not evidence of a universal 95-point client result.

After release, watch field observations over their actual reporting period rather than expecting an immediate replacement of historical data. Check business outcomes separately. Neither a good INP result nor a particular Lighthouse score guarantees a ranking or an increase in enquiries.
